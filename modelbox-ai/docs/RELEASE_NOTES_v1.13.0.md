# ModelBox AI — v1.13.0 Release Notes

**Tag:** `v1.13.0`, on `main`, published by the gated release workflow  ·
**Carries:** Sprint 9, merged to `main` in pull requests #27 to #35 and the
release-preparation change that set every version stamp to 1.13.0  ·
**Supersedes:** v1.12.0.

**This release finishes the engagement's deliverables and keeps SQL Server and
Oracle models' meaning when they are exported to PostgreSQL.** A
source-to-target mapping now accounts for every target column, and every
decision in it is a person's. Types, identities, sequences, computed columns
and pattern checks carry over to PostgreSQL where they can, and are named where
they cannot. ModelBox suggests which columns hold PII, and which column each
table's measures should be aggregated over, and a person decides each
suggestion. Semantic-layer exports sum money columns and not keys or codes,
and an imported schema's MetricFlow semantic model is accepted by dbt.

---

## Upgrading an existing install

1. **Check out `v1.13.0` and start the appliance as before** (`up --build -d`,
   README "Quick start"), or run the published v1.13.0 images (README
   "Releases"). No `.env` change is needed. One optional setting is new:
   `PII_RULES_PATH`, a file of your own PII suggestion rules (user guide,
   "Suggestions").
2. **The migrate service upgrades the database on start.** It runs migrations
   0028 to 0031 in order, then exits; the backend starts after it. Nothing is
   run by hand, and no existing value changes.

   | Migration | What it does |
   | :-- | :-- |
   | 0028 | Adds each imported column's identity (seed and increment, or the trigger and sequence that fill it) and each model's sequences. |
   | 0029 | Adds each imported computed column's expression, as declared, and whether the source stores it. |
   | 0030 | Adds source-to-target mapping documents, entries and proposals, and the append-only record of every mapping decision; adds three audit actions. |
   | 0031 | Adds suggestions, stored beside the model, and one audit action. |

## Compatibility: exports that change

Three changes alter files an existing consumer may already use. Re-export, and
check anything that reads these files by name.

**(a) Semantic exports of imported schemas use valid MetricFlow names, so names
may change.** MetricFlow accepts only lower snake case names, and an imported
schema's names are the source's own. A MetricFlow export of an imported schema
now writes them in lower snake case (`SalesOrderHeader` becomes
`sales_order_header`). A name that would collide takes its table's name (the
dimension over `SalesOrderDetail.ProductID` becomes
`sales_order_detail_product_id`), a repeated measure takes its table's name,
and a table's second foreign key to the same table, or one to itself, is named
after its column and listed as an export gap instead of joining. Each `expr`
keeps the column's own name, so the SQL it reads is unchanged, and
`EXPORT_NOTES.md` lists the changes. **The reference models are unchanged**:
their names were already valid. Before this release, such an export was
refused by `dbt parse` once a table had an aggregation time column.

**(b) dbt exports with no dialect named are cast to Snowflake types.** A dbt
project's staging models now cast each column to its type in the warehouse the
project runs on, as the DDL export writes it for that dialect. The export's
`dialect` parameter defaults to `snowflake`, so a dbt export that names no
dialect is cast to Snowflake types; in v1.12.0 it cast to the types the source
declared. Choose the warehouse when you export, in the export panel or with
`dialect=`. Names that are not lower snake case are now quoted.

**(c) Which columns are measures changes in semantic exports.** Money columns
are now summed as measures, and keys, foreign keys and integer codes are
dimensions (below). A MetricFlow, Cube or LookML export can therefore gain
measures over amounts and lose measures it had over codes and keys.

## What's new

### Exports to PostgreSQL keep their meaning

- **Types:** SQL Server `money`, `smallmoney` and `bit` are written as
  `NUMERIC(19, 4)`, `NUMERIC(10, 4)` and `BOOLEAN`, with a `bit` column's `0`
  and `1` in defaults and CHECKs written `FALSE` and `TRUE`. `hierarchyid` and
  `geography` are written as `LTREE` and PostGIS `GEOGRAPHY` only when the
  export says the target has the extension (`target_has_ltree`,
  `target_has_postgis`, off by default); the file then creates the extension
  first. Otherwise the column is a named gap.
- **Identity columns** keep their seed and increment, as
  `GENERATED BY DEFAULT AS IDENTITY` on an integer type, or as a sequence
  default on Oracle's `NUMBER(*,0)`, which is named. A column an Oracle trigger
  fills from a sequence is named. **A PostgreSQL model's sequences** are
  created, and their defaults kept.
- **Computed columns:** a SQL Server computed column is exported as a
  PostgreSQL generated column where its expression carries over (column
  references, literals, arithmetic, `ISNULL` as `COALESCE`, `CONVERT` as `CAST`,
  and `+` on strings as `||`), labelled by whether the source stores it. Any
  other expression is a named gap quoting it. AdventureWorks exports seven and
  names three.
- **Pattern checks:** a T-SQL `LIKE` character class (`[A-Za-z]`, `[0-9]`,
  ranges and sets) in a CHECK is written as `SIMILAR TO`, with the same
  meaning; a pattern outside that subset is a named gap.
- **Collation is named.** SQL Server's default collations compare text
  case-insensitively and PostgreSQL's does not. An export of a SQL Server model
  names a `collation` gap on each table with a text key, a UNIQUE on text, or a
  pattern CHECK.

Each of these is applied to a real PostgreSQL 16 in CI (Proof Log PL-026 to
PL-028).

### dbt projects and seed data for imported schemas

- A dbt project exported from an imported schema builds on PostgreSQL: the
  change above, and every name quoted where it must be. `dbt build` passes on
  the four certified fixtures in CI (PL-007).
- **Seed data satisfies every primary key, UNIQUE, foreign key and CHECK** the
  model declares, each column generated for its target type, computed columns
  not written. A row no values can satisfy is left out and counted in
  `rows_skipped` (PL-014).

### Source-to-target mapping

- A mapping document maps a source model's columns to a target model's. Every
  target column is **mapped** (one-to-one, or many-to-one with the
  transformation stated), **explicitly unmapped** (a constant, derived, or not
  yet mapped), **pending** (only proposals), **silent** (nothing), or **in
  drift** (its source or target column is gone: flagged and kept, never
  dropped). The document states "N of M target columns mapped, K explicitly
  unmapped, S silent", and is complete only when nothing is pending, silent or
  in drift.
- **Proposals** carry a name-similarity and a type-compatibility score and a
  confidence, and count as nothing until a person accepts, edits or rejects
  them. Every decision records who made it, when and what was shown, in an
  append-only record, and needs a person signed in: an API key cannot make one.
- Exports as **CSV, Markdown, HTML and JSON**, a lineage view per target
  column, and a **Mapping** panel on the canvas (PL-029).

### Suggestions: PII and the aggregation time column

- ModelBox suggests **which columns hold PII**, from named rules that read
  column names, types, source comments and CHECK constraints. Each category is
  anchored on NIST SP 800-122 §2.2, or on GLBA's nonpublic personal
  information, 15 U.S.C. § 6809(4)(A). A suggestion carries no score, and no
  accuracy figure is claimed. Thirteen PII types are added.
- It ranks **every date or time column** as a candidate for a table's
  aggregation time column, flagging a row-audit column (`ModifiedDate`,
  `created_at`, `updated_at`, a row version) at low confidence. The confidence
  is a ranking from written rules, not a probability.
- A suggestion is stored beside the model and never changes it. A MEMBER or
  above accepts or rejects it; an accepted PII value is pending review, and
  only an approver can verify it. A table declares semantic-layer measures only
  once a person has chosen its time column. Clients can add rules with
  `PII_RULES_PATH`. A **Suggestions** panel on the canvas (PL-030).

### Semantic-layer exports: what is summed, and MetricFlow on imported schemas

- **Money columns are measures.** SQL Server `money` and `smallmoney` and
  PostgreSQL `money` are read as numeric in the MetricFlow, Cube and LookML
  exports, so an amount is summed. Earlier releases wrote such a column as a
  dimension.
- **Codes are not summed.** Keys, foreign keys and integer codes (an integer
  with permissible values, a CHECK allowing few values, or a name that reads
  as a code or an identifier, such as `Status` or `RevisionNumber`) are
  dimensions. A column declared a metric is still a measure unless it is a
  key. `EXPORT_NOTES.md`, beside the exported files, lists each such column
  and why.
- **MetricFlow accepts an imported schema's semantic model.** Names are written
  in lower snake case, as MetricFlow requires, and a name that would collide is
  given its table's name; each `expr` keeps the column's own name, and the
  notes list the changes. A second foreign key to the same table, or one to the
  table itself, is named after its column and listed as an export gap rather
  than joined. `dbt parse` accepts the semantic model of each certified import
  with its time columns confirmed, in CI (PL-011).

### Verified in CI

- **The rollback below** runs on every change: the database is downgraded to
  v1.12.0's schema and v1.12.0's published images run on it.
- The **claims guard** also bars an accuracy figure for finding PII on any
  public surface.

## Rolling back to v1.12.0

Tested in CI on every change (`tests/blackbox/test_rollback.py`): this
release's database is downgraded to v1.12.0's schema, and v1.12.0's published
images start on it, report healthy, and read the models.

1. Stop the application, keeping the database:

   ```bash
   docker compose --env-file .env -f docker/docker-compose.appliance.yml stop modelbox-ui modelbox-backend modelbox-worker
   ```

2. Downgrade the schema **while still on v1.13.0**: its image holds the
   downgrade steps, and v1.12.0's does not. Take a backup first; the losses
   below cannot be undone by upgrading again.

   ```bash
   docker compose --env-file .env -f docker/docker-compose.appliance.yml run --rm --no-deps modelbox-migrate python -m alembic downgrade 0027_member_audit_actions
   ```

3. Check out the `v1.12.0` tag, keeping the same `.env`, and start the
   appliance as its README describes. Its migrate service finds the database
   already at its head and changes nothing.

**What the downgrade loses.** v1.12.0's schema has no place for the following,
and they are deleted, not kept aside:

- every mapping document, with its entries and proposals;
- every suggestion, whether pending, accepted, rejected or superseded;
- each imported column's identity (seed and increment, or its trigger and
  sequence) and each model's sequences;
- each computed column's expression and whether the source stores it;
- **a PII type added in this release**, on any column that holds one: the
  column stays marked PII with no type, because v1.12.0 cannot read the type.
  A verified `pii` field on that column returns to pending review, with an
  audit event, and each such column is listed in the model's conversion
  findings (kind `pii_type_cleared`).

**What it keeps:** the **record of every mapping decision** (who decided what,
when, and what was shown), still append-only; models, with every value a
person accepted from a suggestion (an aggregation time column, a PII flag, a
PII type v1.12.0 reads); workspaces, members, API keys and the audit trail.
Audit events written by v1.13.0 (mapping and suggestion decisions) stay in the
append-only audit log, and the database keeps accepting their action names;
v1.12.0 never writes them. After the rollback, exports are v1.12.0's: computed
columns and the new type mappings are named gaps again.

The test asserts by SQL: the mapping and suggestion tables are gone; the
identity, computed-expression and sequence columns are gone; a newer PII type
is cleared with the column still PII and listed once, while an older type is
kept; the decisions record keeps every row; and the audit events stay. v1.12.0
then reads the HR, Pagila and AdventureWorks models. The rest of the list is
read from the migrations' downgrade steps.

## Known limits

- **Collation is not captured**, only named as a gap.
- **Snowflake import is not certified.** Its fixture is written from
  documentation.
- **Mapping transformations are recorded, not run**, and mapping columns are
  picked from lists, not on the canvas.
- **OIDC sign-in in the UI is not built.** Server verification exists.
- **LookML stays Preview.** No offline parser exists to check it; the Cube and
  MetricFlow exports are the ones checked by their tools.
